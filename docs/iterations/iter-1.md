## 1. 目标

走通一条最小但完整的流程：**TMDB 采集 → 自动初筛 → 网页审核 → 浏览 / 搜索 → 手动标记片源状态**。
范围只限试点：按品牌发现 **BBC Earth（UK-2）**、**Netflix（ST-1）**；按重点栏目直接跟踪 **NOVA、Horizon、Inside the Factory**。
这个迭代的重点是验证**数据结构和基本流程对不对**，不追求数据全。

## 2. 包含的功能

| # | 内容 | 具体做什么 |
|---|---|---|
| 1 | 网络客户端 | `core/http.py`：境外来源走 `PROXY_URL`，超时、最多 3 次重试（指数退避，429 按 `Retry-After` 等待）、限速（TMDB 每秒约 4 个请求，远低于官方上限）、统一 User-Agent；日志和报错里把 `api_key` 换成 `***` |
| 2 | 密钥 | `.env` 新增 `TMDB_API_KEY`（你申请到的 32 位 API Key）。只有跑 TMDB 采集时才要求；没填时报“`.env` 里缺 TMDB_API_KEY”，网页和其他命令照常用 |
| 3 | TMDB 采集 | `sources/tmdb.py`：<br>• **按品牌**：`discover/tv`，纪录片类型 99 + 品牌的播出方编号、出品公司编号分别查再合并去重；首播日期从品牌 `start_year` 起<br>• **重点栏目**：按 `tmdb_tv_id` 直接取详情，不看类型<br>• **详情**：`tv/{id}` 一次请求带上 `keywords`、`external_ids`、`translations`（中文标题和简介从这里拿，省掉第二次请求）<br>• **季和集**：长青栏目（三个试点栏目都是）取 `since_year`（2010）以后每一季的 `tv/{id}/season/{n}`，建季和集；普通系列只建季（集数、首播日期来自详情），**不逐季取集**（Netflix 几百部，逐季取请求太多；以后要用再加）<br>• 第 0 季（特辑）不收 |
| 4 | 原始数据 | 每个 TMDB 返回原样压缩存进 `<DATA_DIR>/raw.db`（`raw_record`），内容没变不重复存。以后 `doc reclassify` 用它重新判断（`reclassify` 本身在迭代 2a 做） |
| 5 | 初筛 | `pipeline/prescreen.py` + 新文件 `config/rules.yaml`。每条给出**建议（收录 / 排除）+ 理由 + 主题**：<br>• 主题：栏目预设主题 → 品牌默认主题（BBC Earth = 自然）→ TMDB 关键词映射 → 标题/简介关键词（中英文）<br>• 排除提示：TMDB 关键词或简介命中“true crime、reality、sport、music、biography、politics”等 → 建议排除并写明命中了什么<br>• 语种：原始语种不是英文/中文 → 建议排除，理由“非中英原产，需确认有英文配音”（你审核时可改）<br>• 打不上主题的 → 不给建议，理由“未判断出主题，需人工”<br>初筛**只给建议，不直接排除**，最后由你在审核页决定 |
| 6 | 跟踪状态 | 按品牌发现 → `待审核`；重点栏目 → 直接 `已收录`；首播日期在未来 → `待播`。每次变化写 `status_event`（谁改的、理由、哪次任务）。同一 TMDB 编号只建一条作品：已排除的再次被发现不会再进审核 |
| 7 | 命令 | `doc discover --source tmdb`，可选 `--brand UK-2`（或 `--series nova`）只跑一个品牌/栏目，`--dry-run` 只抓取和初筛、列出“会新增什么”，**不写任何数据库**。结束时打印汇总（新增几条、各品牌几条、建议收录/排除各几条、请求数），并写一条 `run` 记录 |
| 8 | 检查时间 | `source_checkpoint` 按“tmdb + 品牌 / 栏目”分别记。第一次从品牌起始年份全部拉一遍；之后只查上次成功以后首播的新系列。某个品牌失败不影响其他品牌，下次从它自己的上次成功时间接着查 |
| 9 | 网页：首页 | 原有内容 + 简单统计：待审核数、已收录数、计划中数、最近一次 `discover` 的结果 |
| 10 | 网页：审核页 | 待审核条目按品牌分组；每条显示海报、中英文标题、年份、原始语种、简介、初筛建议和理由、主题。操作：逐条收录 / 排除（排除时可选写理由）；**整组**“全部收录”“按建议处理”（建议收录的收录、建议排除的排除、没建议的留着）；收录时可以改主题 |
| 11 | 网页：作品列表 | 全部 `已收录` 作品；按品牌、主题、年份、类型、片源状态筛选；按年份、TMDB 评分、标题排序 |
| 12 | 网页：待下载 | `已收录` 且未全部入库的作品，默认按 TMDB 评分从高到低；筛选同上；“只看计划中” |
| 13 | 网页：详情 | 海报、中英文标题、简介、品牌、主题、TMDB 评分（带拉取日期）、TMDB / IMDb 链接；季列表（普通系列每季一个片源状态）；长青栏目按季折叠的集列表（每集一个片源状态，另有“整季标记”）；跟踪状态和状态变化历史；可以手动改跟踪状态 |
| 14 | 片源状态 | `未入库` / `计划中` / `已入库` 一键切换（htmx，不刷新页面），列表页和详情页都能点。系列整体显示“3/5 季已入库”，长青栏目显示“已入库 12 集” |
| 15 | 搜索 | 顶部搜索框，中英文标题。三个字及以上用 SQLite 全文检索（trigram），一两个字用模糊匹配 |
| 16 | 数据库 | 迁移 0002 建表：`brand`、`series_watch`、`theme`、`title`、`season`、`episode`、`external_ref`、`title_theme`、`status_event`、`source_checkpoint`、`rating`（见第 4 节）；`raw.db` 单独建。品牌、栏目、主题每次运行时从 `config/*.yaml` 同步进数据库 |
| 17 | 测试 | 单元：初筛规则、状态流转、片源状态汇总、检查时间、`api_key` 脱敏。集成：用存好的 TMDB 响应样例（`tests/fixtures/tmdb/`）跑完整 `discover`，检查写库结果、重复运行不重复建、`--dry-run` 不写库；模拟 401、超时、429。网页：各页面能打开，审核、片源状态切换、搜索中英文都能用 |
| 18 | 文档 | README 加“填 TMDB key、第一次采集”一节；`.env.example` 加 `TMDB_API_KEY`；`CHANGELOG.md` 写 v0.1 |

## 4. 数据模型的两处调整（请确认）

`data-model.md` 里没有地方放“初筛建议”，评分表原计划迭代 2a 才建。建议：

1. **`title` 加两个字段**：`screen_suggestion`（`include` / `exclude` / 空）和 `screen_reasons`（理由列表）。初筛建议和“当前状态的理由”（`tracking_reason`）是两回事：前者是系统的建议，后者是状态为什么是现在这样，分开存，审核页才能同时显示。
2. **`rating` 表提前到迭代 1 建**，本迭代只存 TMDB 评分（`source = tmdb`）。这样待下载页能按评分排序；字段和 `data-model.md` 一致，2a 直接往里加 IMDb 评分，不用再改表。

## 7. 需要你准备 / 决定的

1. **准备 TMDB API key**：按 `sessions.md` 第 6.1 节申请（免费，约 10 分钟），验收前填进你电脑上项目文件夹的 `.env`：`TMDB_API_KEY=你的key`。**不要发在对话里**。写代码期间用不到，验收时才需要。
2. **第 4 节的两处数据模型调整**（`title` 加初筛建议字段；`rating` 表提前到迭代 1，只存 TMDB 评分）：同意吗？
3. **要不要把 TMDB key 配到云端环境**（可选）：在会话标题栏的云端环境菜单 → 编辑，加到 Network secrets（没有这一栏就加成环境变量），名字 `TMDB_API_KEY`；新开的会话才能读到。好处是我能在云端跑真实采集、用真实返回做测试样例，你验收时少来回；不加也可以，按第 5 节的方式走。key 只在你自己的云端环境里，不会出现在对话和仓库里。
4. 以下默认做法，不同意直接说：
   - 普通系列只建季、不建集；长青栏目建到集（第 2 节第 3 条）
   - 非中英原产的作品**建议排除**（不是直接排除），由你审核决定
   - 本迭代只做电视系列，Netflix / BBC Earth 的纪录长片放到 2a 和评分门槛一起做
   - 品牌参数用编号：`--brand UK-2`、`--brand ST-1`（大小写都行）；栏目用简称：`--series nova`
   - 在 `--dry-run` 下原始数据也不保存（完全不写任何文件）
